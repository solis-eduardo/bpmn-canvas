# Class names drop the aggregate prefix unless two aggregates collide

As the architecture refactor split controllers/policies/services by sub-resource (Lock, Fork, Collaborator, Member, Owner), we needed a consistent naming rule instead of deciding prefix-or-not case by case. We decided a class is named after its own concept alone (`LockController`, `ForkService`, `CollaboratorPolicy`, `MemberController`) and only gets the owning aggregate's prefix when the same concept name would otherwise be ambiguous between two aggregates that both have it — today that's just `Owner` (`DiagramOwnerController`/`WorkspaceOwnerController`, since both Diagram and Workspace have one) and Diagram's own `Workspace`-placement sub-resource (`DiagramWorkspaceController`, to avoid colliding with the `Workspace` aggregate's own controller). This applies even to `Collaborator` and `Member`, which rename their Models/tables (`diagram_collaborators` → `collaborators`, `workspace_members` → `members`) along with their classes — we accepted that migration cost for naming consistency rather than carrying a prefix neither concept needs. Notifications are the one exception: they keep the originating aggregate's prefix (`WorkspaceMemberAdded`, not `MemberAdded`) because they're read out of context — in a queue, a log, an email — where the bare concept name alone wouldn't be legible.
