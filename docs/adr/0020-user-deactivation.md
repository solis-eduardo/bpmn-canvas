# Deactivating a User account

Status: accepted

An Administrator can deactivate a User (issue #244). Deactivation is a state on the account (`deactivated_at`, null when active), not a deletion: the User's authorship and history stay in place, and reactivation restores access.

**Rules:** a deactivated User can't sign in by either login method. Their sessions and remember-me token are revoked (`UserSessionRevoker`), and a session that survives (file or cookie drivers, which can't be enumerated by User) is signed out on its next request. Their Locks are released through the normal release path, so unsaved content is kept as a provisional Version. Active Users are the default: `User` carries a global scope (`ActiveUserScope`), so every listing, picker, lookup, route binding and validation (`activeUserRule()`, not `exists:users`) returns active Users only, and a deactivated id fails like an unknown one (an email that matches one is answered like an email that matches nobody). Only User administration (the Users list, the edit screen, deactivate/reactivate, ownership transfer), written as `User::withDeactivated()`, and the login lookups (local, Keycloak, demo, which must find the account to refuse it) opt out; the session guard uses a User provider that still resolves a deactivated User so `EnsureUserIsActive` can sign them out. Records that already point at a deactivated User keep resolving it: the Diagram Owner and Author, Lock holder and requester, Share creator, Workspace Owner and the user of a Collaborator or Member row load it through relations that opt out of the scope. Their Collaborator and Member rows are kept, so reactivation needs no re-invitation, but lists and counts of Collaborators and Members skip them (`ofActiveUsers`). A deactivated User receives no notifications (a `NotificationSending` listener cancels them). Diagrams and Workspaces they own stay owned by them and are listed on the User's edit screen; an Administrator can transfer all of them to an active successor in one action (Diagram Owner transfers drop the previous owner's access entirely, an explicit exception to the default in CONTEXT.md ("Diagram Owner") and ADR-0017, since the previous owner is deactivated; Workspace transfers keep them as a Member). Administrators can't deactivate their own account; since the acting Administrator is always another active one, at least one Administrator always remains. Authorship is never touched (CONTEXT.md, "Author").

**Why:** deleting the account would orphan authorship, Versions and Notifications; a plain flag keeps the history and makes the action reversible. Ownership is handed over explicitly rather than automatically, because only a person can choose the right successor. Revoking sessions alone is not enough for every session driver, so the request-time check is the backstop.

**Why a default scope:** filtering picker by picker (the first attempt) left every other lookup and validation leaking deactivated Users. A scope that is on unless asked off makes the safe behaviour the default and the exceptions explicit and greppable (`withDeactivated`, `withoutGlobalScope(ActiveUserScope::class)`).

**Consequences of the default scope:** the owner and author filters of the Diagram and Workspace lists offer active Users only, so what a deactivated User still owns is found from their edit screen in User administration. The Collaborator and Member rows of a deactivated User can not be addressed from the Diagram or Workspace screens (their routes answer 404); they stay until reactivation. A notification addressed to a deactivated User, such as an access request to a deactivated Diagram Owner, is dropped without feedback to the sender.
