# Lock released explicitly or by expiry

The legacy stack was explicit about having no concurrent editing lock at all: "if two people save the same file, the last one wins." That was acceptable with a single shared username/password, but with individual accounts (ADR-0001) and per-Diagram Collaborators, silent collisions become a real risk of lost work.

A Lock is held per Diagram: opening another Editor does not replace or release a User's existing Locks. Leaving or closing the Editor does not release the Lock by itself. The holder can release each Lock explicitly, and an Administrator can force-release it. The holder's open Editor sends a Heartbeat every 30 seconds while the holder is actively using it; a Lock that goes **3 minutes without a Heartbeat expires** and is released by the scheduled `locks:expire` command (TTL configurable through `LOCK_TTL_MINUTES`). Other eligible Users can request a held Lock, which notifies the holder but never transfers the Lock automatically, including after 30 seconds. A Fork (independent copy of the Diagram) remains an immediate alternative for someone who cannot wait.

The Heartbeat carries the Editor's unsaved content when there is any, kept on the Diagram as a draft. When a Lock expires, the draft (if any) is saved as a **provisional Version** attributed to the former holder, named "Provisional version (Lock expired)", before the Lock is released. A normal save discards the draft, since the content is then a regular Version. This way an expiry never loses the holder's last synced work.

A manual release offers the same choice. The holder's own release, when the Editor has unsaved changes, and an Administrator's force-release, when the server holds a draft (the Lock state reports `has_draft`), ask whether to save the draft as a provisional Version, discard it, or cancel. Saving writes the Version in the holder's name before the Lock is released, so a failed save leaves the Lock and draft untouched. When the holder releases, their Editor sends its latest content with the request, newer than the last Heartbeat; an Administrator's request can only save what the server already holds. As with expiry, a blank draft, or a holder who can no longer edit, is skipped and the Lock is released. The Version is named for what happened, "Provisional version (Lock released)", while the one kept by an expiry (or by taking over an expired Lock) stays "Provisional version (Lock expired)"; the reason is stored with the Version's state, and Versions kept before it was recorded read as expired (issue #263).

We first chose explicit release only, because browser/tab lifecycle alone is not a reliable sign that editing has ended, and that left an abandoned Lock able to block editing indefinitely. Expiry is safe now because it is not driven by the tab lifecycle: the Heartbeat stops only after the Editor was closed or untouched for 2 minutes, and the unsaved content is preserved as a Version instead of being discarded. Expiry only ever **releases**: it never transfers the Lock to a requester (ADR-0011 still requires a human picking the recipient). The trade-off is that a holder who is idle for more than the TTL loses the Lock and has to acquire it again, possibly finding it taken, in which case their last content is in the Version history.

Whoever opens a locked Diagram gets the read-only Viewer instead of the Editor: a red notice names the holder, saving is impossible, and the only actions are requesting the Lock (or, for an Administrator, force-releasing it).

Rendering a page never takes the Lock. The Editor acquires it with `POST /diagrams/{slug}/lock` once its page has loaded, before it starts, and the server answers for that acquisition with its own authorization (the User must be able to edit) and with a 423 when someone else holds the Lock. A refused acquisition sends the User to the read-only Viewer: the Editor navigates to the Diagram's show URL, and the server renders the Viewer for a Diagram someone else holds. The Viewer's "request the Lock" action is a separate endpoint, `POST /diagrams/{slug}/lock/request`, the only one that notifies the holder. This way a prefetch, a link preview or a tab restored at startup, which fetch the page without a person behind it, leave the Lock alone. Users without edit permission are a separate case: they never reach the Diagram at all (an Administrator sees it in the Viewer, per ADR-0006).

An expired Lock that `locks:expire` has not released yet does not block that acquisition: the acquisition takes it over at once, in one conditional write that only matches while the row still shows the holder and the last Heartbeat it observed, and that Heartbeat is older than the TTL. Two takeovers at once, or a takeover against the former holder's late Heartbeat, cannot both win (and a Heartbeat is itself conditional on its sender still being the holder). The former holder's draft is kept as a provisional Version in the same transaction, exactly as the expiry command would have done, and their next Heartbeat or save is refused as a lost Lock.

## Amendment: the Lock follows edit rights

Release was originally only explicit or by expiry, so each path that removed a holder's right to edit handled the Lock on its own, and some never released it (a Keycloak group sync, taking a Diagram out of or moving it between Workspaces, a Diagram Owner transfer that gives up access). The former editor kept showing as the holder, and blocked everyone else, until the Lock expired (issue #231). The Lock is now reconciled after every access change: it is released as soon as its holder can no longer edit the Diagram. The paths covered are removing a Collaborator, removing a Member or a Member leaving, a Keycloak group sync that drops membership, assigning or removing a Diagram's Workspace, and a Diagram Owner transfer that gives up access. The Lock is released only if the holder can no longer edit: one who keeps access another way (as Diagram Owner or Collaborator) keeps it. A membership change reconciles every Lock the User holds on Workspace Diagrams: those of the Workspace they left or were removed from, and, for a Keycloak group sync, those of any Workspace.

This release **discards the holder's draft** instead of saving it as a provisional Version, as the existing handling of a holder who has lapsed already did: the provisional Version would be authored by someone who may no longer edit the Diagram. The consequence is that unsaved work since the holder's last save is lost when their access is revoked.

The Heartbeat still re-checks edit rights live. The rest of this ADR is unchanged: the TTL and the saving of the draft on expiry still apply, and none of this transfers the Lock (ADR-0011). Deactivating a User (ADR-0020) is a separate path: it releases their Locks with the draft kept as a provisional Version.

## Amendment: shorter idle and expiry intervals

The Editor now stops sending Heartbeats after **2 minutes** without user activity (it was 3), and the Lock expires **3 minutes** after its last Heartbeat (it was 5; default `LOCK_TTL_MINUTES` = 3). The last Heartbeat goes out at the end of the idle window, so the intervals add up: an abandoned Lock is released about **5 minutes** after the holder's last interaction, down from about 8. The behaviour itself is unchanged: idle tabs stop renewing, and the server releases the Lock and keeps the draft as a provisional Version. The figures in the text above were updated in place to match.
