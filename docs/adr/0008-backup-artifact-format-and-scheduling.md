# One tar.gz artifact per backup run, dumped by a dedicated scheduler service

Status: accepted

Losing the host previously meant losing every Diagram's content, its Version history (ADR-0004's per-Diagram `.git` repositories), and the database (Users, Shares, Workspaces, everything relational) in one shot, with nothing automated in place to prevent it.

**A backup run produces exactly one artifact: a single `.tar.gz` containing a `diagrams/` copy and a `database.dump`.** We rejected backing up the Diagrams directory and the database on separate schedules (e.g. a filesystem snapshot for `diagrams/` and a nightly `pg_dump` on its own cadence), because a Diagram row and its on-disk `.git` history only make sense together, and Diagram content also references database state (the `disk_path` in the `diagrams` table); two artifacts from two different moments could point at each other inconsistently. A restore command (ticket 05, not part of this decision) can then reason about "one backup" as one file instead of reconciling timestamps across two locations. `database.dump` uses `pg_dump --format=custom` rather than plain SQL, so it's directly consumable by `pg_restore` (including selective/parallel restore) instead of forcing a full SQL replay. A `manifest.json` (format version, creation time) rides along so a future restore can validate an artifact before touching anything, without parsing the tarball's other members first.

**The scheduler is its own Compose service, not host cron.** `bootstrap/app.php` registers `backup:run` via Laravel's `withSchedule`, and a dedicated `scheduler` service runs `php artisan schedule:work` continuously. We rejected a host crontab entry (the legacy stack's approach for Diagram versioning before ADR-0004 formalized it — see that ADR) because it lives outside the repo and the compose stack: it isn't reviewed with the code, doesn't come up automatically when the stack does, and ties the schedule to whichever host happens to run it. The scheduler service shares the `diagrams` volume (mounted read-only — it only ever reads) and gets its own `backups` volume for the destination, but never runs migrations itself: `app` already owns that, and two containers racing `migrate --force` against Postgres on startup is a hazard worth avoiding for a service that has a full day (the default `dailyAt` schedule) to tolerate `app` finishing its own startup first. The service also declares `depends_on: app: service_healthy`; since `app` only turns healthy after its entrypoint has migrated, the schema is guaranteed to exist before the first run.

**Destination and retention are environment-driven, defaulting to a host-mounted volume with 14 days.** `BACKUP_DESTINATION` backs a `backups` filesystem disk (parallel to the existing `diagrams` disk), and `BACKUP_RETENTION_DAYS` (default 14) is applied by `backup:run` itself pruning artifacts past that window on every run, rather than depending on an external tool (e.g. `logrotate`, a cloud lifecycle policy) that would need separate configuration outside the app. We rejected hardcoding the destination, since operators who move backups straight to network storage or another mounted volume shouldn't need a code change to do it.

## Consequences

- A future restore command (ticket 05) can rely on the artifact's fixed layout (`diagrams/`, `database.dump`, `manifest.json`) instead of re-deriving it from `backup:run`'s implementation.
- Retention is based on the timestamp encoded in each artifact's filename (`backup-<Y-m-d_His>-<random>.tar.gz`), not the file's filesystem mtime, so pruning follows the application clock (testable via time-travel) rather than the host clock. The artifact is archived under a `.part` name and renamed into place only once complete, so a listing (or a restore command) never sees a partially-written file under its real name.
- If Postgres and the Diagrams volume ever diverge in how they're backed up in the future (e.g. moving to managed Postgres with its own point-in-time recovery), this decision should be revisited — it assumes both are ordinary, host-adjacent stores.
